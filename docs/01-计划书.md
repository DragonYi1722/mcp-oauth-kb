## 一、项目背景与问题

### 1.1 业务背景

企业知识库是 MCP（Model Context Protocol）最典型的落地场景之一：员工希望直接对 AI 助手说"帮我找一下上季度的复盘文档"，而不是打开多个系统逐个搜索。把知识库封装成 MCP Server 后，Claude、IDE 助手、内部 Agent 都可以通过统一的工具接口访问文档。

但"能访问"和"能安全地访问"是两件事。一个只做了功能、没做授权的 MCP Server，通常会落入以下陷阱：

- **静态 Token / API Key**：把长期有效的密钥写进客户端配置，一旦泄露无法细粒度撤销；
- **权限过大**：所有调用者都能读写全部文档，没有"部门 / 个人 / 全公司"的可见性边界；
- **身份不可信**：工具参数里直接传 `user_id`，调用者可以冒充任何人；
- **无审计**：不知道谁在什么时候读取或修改了哪篇文档；
- **Token 透传**：Server 把客户端 token 原样转发给上游 API，形成混淆代理（confused deputy）。

### 1.2 标准背景

MCP 规范在 **2026-07-28** 版本中把 OAuth 2.1 作为面向不可信客户端的强制基线，并明确了角色分离：

- **MCP Server = OAuth Resource Server（RS）**：只负责校验 token，不再兼任授权服务器；
- **Authorization Server（AS）**：独立部署，负责登录、同意、签发与刷新 token；
- Server 必须发布 **RFC 9728 受保护资源元数据**，校验 token 的 **audience（RFC 8707）** 与 **issuer（RFC 9207）**；
- 授权码流程强制 **PKCE S256**；
- 客户端注册的优先顺序为：**预注册 → CIMD（Client ID Metadata Document）→ DCR → 提示用户**，其中 DCR（RFC 7591）在新规范中已被标记为弃用方向。

### 1.3 要解决的问题

本项目要回答一个具体问题：

> 如何让一个企业知识库 MCP Server 在"AI 客户端可自由接入"的前提下，仍然做到**身份可信、权限最小、数据隔离、行为可审计**？

## 二、项目目标

### 2.1 总目标

实现一个可一键启动、可演示、可测试的企业知识库 MCP Server：

1. 客户端通过标准 OAuth 2.1 授权码 + PKCE 获取 token；
2. Server 在本地完成 JWT 验签与 `iss` / `aud` / `exp` / scope 校验；
3. 权限模型把 scope 映射到具体工具，把用户身份映射到具体数据；
4. 所有工具调用写入审计日志；
5. 用负向测试证明上述机制"真的能挡住攻击"。

### 2.2 量化指标

| 维度 | 指标 | 验收方式 |
|---|---|---|
| 功能 | 6 个 MCP 工具、3 类角色、3 个 scope | Inspector 逐项调用 |
| 授权 | 未登录请求 100% 返回 401 + PRM 指引 | 自动化测试 |
| 验签 | 错误 `aud`、错误 `iss`、过期 token 100% 拒绝 | 负向测试 |
| 隔离 | 三个测试用户检索结果按权限不同 | 集成测试 |
| 审计 | 每次调用可追溯到 `sub`、工具、结果、耗时 | 查询审计表 |
| 工程 | `docker compose up` 后 10 分钟内可完成 Demo | 按 README 复现 |
| 质量 | 核心授权路径测试覆盖率 ≥ 80% | `pytest --cov` |
| 交付 | 计划书、工程方案、安全设计、Demo 视频、技术博客 | 文档清单 |

### 2.3 非目标（明确不做）

- 不做通用 RAG / 向量数据库平台（pgvector 仅作为可选进阶）；
- 不手写 OAuth 授权服务器（使用 Keycloak，避免自研密码学与协议细节）；
- 不做生产级计费、多组织 SaaS、移动端；
- 不追求前端 UI 的完整度，管理页仅用于演示。

## 三、用户角色与用户故事

### 3.1 角色

| 角色 | 说明 | 默认 scope |
|---|---|---|
| 员工（alice） | 普通知识库使用者 | `kb.read`、`kb.write` |
| 部门经理（bob） | 管理本部门文档 | `kb.read`、`kb.write` |
| 管理员（admin） | 全局管理、归档 | `kb.read`、`kb.write`、`kb.admin` |
| AI 客户端 | 代表用户调用工具 | 继承用户授权 |
| 未登录访客 | 无任何权限 | 无 |

### 3.2 用户故事与验收标准

**US-1 搜索文档**
作为员工，我希望用自然语言关键词搜索我可见的文档，以便快速找到资料。
- 验收：返回结果只包含 `private(本人)`、`department(本部门)`、`org(全公司)` 三类可见文档；分页参数生效；空结果返回空数组而非报错。

**US-2 创建文档**
作为员工，我希望创建文档并自动归属到自己和所在部门。
- 验收：`owner_id` 必须等于 token 的 `sub`；请求中即使伪造 `owner_id` 也被忽略；创建后立即可被本人检索到。

**US-3 更新文档**
作为员工/经理，我希望更新我有权修改的文档。
- 验收：只有 owner、同部门经理或管理员可以更新；越权返回 `404 NOT_FOUND`（避免泄露文档存在性）。

**US-4 归档文档**
作为管理员，我希望归档过期文档而不是物理删除。
- 验收：需要 `kb.admin`；归档后默认检索不可见；审计日志记录操作者与文档 ID。

**US-5 未登录访问**
作为未登录客户端，我访问 MCP Server 时应被引导去登录。
- 验收：返回 `401`，`WWW-Authenticate` 头包含 `resource_metadata` 指向 RFC 9728 元数据；客户端可据此自动发起 OAuth。

**US-6 越权尝试**
作为低权限用户，我尝试读取其他部门私有文档。
- 验收：返回 `404`；审计日志记录 `result=denied`；不泄露标题、正文、owner 等任何信息。

## 四、项目范围

### 4.1 MVP（第 1–8 周，必须完成）

- 6 个 MCP 工具：`whoami`、`search_documents`、`get_document`、`create_document`、`update_document`、`archive_document`；
- Keycloak realm 一键导入（3 个用户、3 个角色、3 个 client scope、Audience mapper）；
- OAuth 2.1 授权码 + PKCE，MCP Inspector 可完成登录并调用工具；
- JWT 本地验签（JWKS 缓存、`iss`/`aud`/`exp`/`nbf`、scope）；
- 工具级授权 + 用户/部门级数据隔离；
- 审计日志；
- Docker Compose 一键启动 + 种子数据；
- pytest 单元/集成测试 + GitHub Actions；
- README、架构图、3 分钟 Demo 视频。

### 4.2 进阶项（第 9–12 周，按剩余时间选做）

- CIMD 完整链路，并与 DCR 做对比；
- Keycloak Identity Brokering 接入 Google / GitHub；
- Claude Desktop 远程连接器；
- TypeScript 客户端 + 极简 Web 管理页；
- pgvector 语义检索；
- 限流、刷新令牌轮换、令牌撤销；
- OpenTelemetry + Prometheus；
- 无状态水平扩展演示（2 个 Server 副本）。

### 4.3 不做

- 自研授权服务器；
- 复杂组织架构与跨租户计费；
- 生产级高可用与灾备。

## 五、技术路线与可行性

### 5.1 技术路线

```
MCP 客户端（Inspector / Claude / CLI）
        │  ① 401 + PRM 发现
        │  ② 授权码 + PKCE
        ▼
Keycloak 26.7（Authorization Server）
        │  ③ 签发 JWT（aud = MCP Server URL）
        ▼
MCP Server（Resource Server，Python + mcp 2.3）
        │  ④ 本地 JWKS 验签 + scope 校验
        │  ⑤ 工具层身份推导 + ACL
        ▼
PostgreSQL 16（文档 / ACL / 审计）
```

关键选择及理由：

| 决策 | 选择 | 理由 |
|---|---|---|
| 协议版本 | MCP 2026-07-28 | 当前规范；无状态设计利于水平扩展，也是面试差异化点 |
| Server SDK | 官方 `mcp` 2.3 | 认证链路可见、可控；避免被框架封装掩盖细节 |
| 授权服务器 | Keycloak 26.7 | 成熟、可 Docker 化、支持 OIDC / CIMD / 联邦登录 |
| 数据库 | PostgreSQL 16 | 事务、行级权限、全文检索；后续可加 pgvector |
| 客户端 | Inspector + Python + TypeScript | 覆盖调试、自动化与跨语言验证 |
| 部署 | Docker Compose + Caddy | 新手可维护；Caddy 自动处理 TLS |

### 5.2 可行性分析

- **技术可行性**：官方 SDK 提供 `TokenVerifier` / `AuthSettings` 示例；Keycloak 官方有 MCP 集成指南；社区已有可参考实现。
- **时间可行性**：10 周、每周 10–12 小时；第 1 周只做 hello world，之后每周一个可验收增量。
- **资源可行性**：本地 Docker 即可完成 MVP；公网演示可选 Cloudflare Tunnel，无需购买域名。
- **学习曲线**：OAuth 2.1 概念较多，因此第 1–3 周安排"先跑通、再理解"的阶梯，每周产出可运行代码。

### 5.3 已知技术风险（详见第七章）

- Keycloak 对 RFC 8707 `resource` 参数仅实验性支持，需要 per-scope Audience mapper；
- CIMD 在 Keycloak 中仍是实验特性；
- MCP 2026-07-28 与旧教程差异大，需严格锁定版本文档。

## 八、验收标准

### 8.1 功能验收

- [ ] `docker compose up -d` 后，Keycloak 控制台可登录，realm `kb` 与 3 个用户存在；
- [ ] `GET /.well-known/oauth-protected-resource/mcp` 返回 RFC 9728 元数据；
- [ ] MCP Inspector 连接 Server，完成浏览器登录后可调用 6 个工具；
- [ ] 三个测试用户执行同一检索，返回结果按权限不同；
- [ ] 归档后的文档默认检索不可见。

### 8.2 安全验收

- [ ] 无 token 请求返回 401 + `WWW-Authenticate`；
- [ ] 错误 `aud` / 错误 `iss` / 过期 token 全部拒绝；
- [ ] 无 `kb.write` 的用户调用写工具被拒；
- [ ] 跨用户、跨部门读取返回 404；
- [ ] 审计日志不包含 token、正文、密码；
- [ ] 负向测试套件 10 类用例全部通过。

### 8.3 工程验收

- [ ] `ruff`、`mypy`、`pytest` 全绿；
- [ ] GitHub Actions 在干净环境可复现；
- [ ] README 让陌生人在 30 分钟内跑通；
- [ ] 文档齐全且与代码一致。

## 十、术语表

| 术语 | 解释 |
|---|---|
| MCP | Model Context Protocol，AI 客户端与工具/数据源之间的开放协议 |
| RS / AS | Resource Server（资源服务器）/ Authorization Server（授权服务器） |
| PKCE | Proof Key for Code Exchange，防止授权码被截获后换取 token |
| PRM | Protected Resource Metadata（RFC 9728），告诉客户端"要登录该找谁" |
| Audience (`aud`) | token 的目标服务；MCP Server 必须确认 token 是签发给自己的 |
| Scope | 权限范围，如 `kb.read`；本项目把它映射到工具 |
| CIMD | Client ID Metadata Document，用 HTTPS URL 作为 client_id 的注册方式 |
| DCR | Dynamic Client Registration（RFC 7591），新规范中已被 CIMD 取代 |
| Confused deputy | 混淆代理攻击：高权限组件被诱导替攻击者执行操作 |
