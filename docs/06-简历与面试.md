## 3. 面试讲解：三个能讲深的故事

### 故事一：身份只来自 token，不来自参数

**背景**：很多 MCP 或 API 项目的工具签名里带 `user_id`，服务端直接拿它查数据。只要客户端能改这个参数，就能读别人的文档。

**做法**：
- 工具函数里没有 `owner` / `user_id` 参数，`create_document(title, content, visibility)`；
- 身份从鉴权中间件写入的上下文取：`actor = current_actor()`，其 `sub` 来自验签后的 token；
- 查询层强制带 `owner_id = sub` 或部门可见性，越权与不存在都返回 `NOT_FOUND`；
- 审计只记录 `actor_sub`，不记录客户端声称的身份。

**结果**：安全测试 `S-09` 里 bob 读 alice 的私人笔记返回 `NOT_FOUND`；即使请求体里塞 `user_id: "admin"`，`whoami` 仍返回 alice。

**可以补一句**：如果确实需要"代操作"，那应该是独立的 token exchange 流程，而不是让客户端传身份。

### 故事二：给 MCP 签 token，audience 却绑不上

**背景**：OAuth 2.1 推荐用 RFC 8707 的 `resource` 参数告诉授权服务器"这个 token 是给哪个服务的"。但 Keycloak 26.7 对它的支持还是实验特性，默认不生效，签出来的 token 没有正确的 `aud`。

**做法**：
- 每个 scope（`kb.read` / `kb.write` / `kb.admin`）配一个 audience mapper，固定 `included.custom.audience = http://localhost:8000/mcp`；
- 服务端 `jwt.decode(..., audience=resource_url)` 强校验；
- 每个 MCP Server 使用独立 scope 名，避免同一 token 带多个 audience。

**结果**：给别的服务签的 token 调本服务返回 401；这条写进了博客和 README 的"已知限制"。

**可以补一句**：这不是 Keycloak 的 bug，而是标准落地节奏问题；换成支持 RFC 8707 的 AS，也应该保留服务端校验，不能只依赖 AS。

### 故事三：CI 从红到绿，三次失败教会我的事

**第一次**：`Wait for the realm` 连接被重置。原因是 Keycloak 启动中会重置连接，而脚本只捕获了 `URLError`。
→ 重试改为捕获 `OSError`，覆盖 reset / 超时 / 拒绝连接。

**第二次**：`compose up` 返回了，但容器还没健康。
→ 改用 `up -d --wait --wait-timeout 300`，让编排层等健康检查。

**第三次**：`pytest: command not found`。集成 job 只装了运行时依赖，`pytest` 在 `[dev]` extra 里。
→ 改成 `pip install -e "apps/mcp-server[dev]"`。

**讲法**：重点不是"我修了三个 bug"，而是"我把三个环境假设变成了显式约束"——启动要等健康、依赖要分运行/开发、重试要覆盖真实错误类型。

## 4. 高频追问与回答

**Q：为什么不用静态 API Key？**
A：Key 只能回答"能不能调"，回答不了"谁在调、能调哪些工具、能看哪些数据、出问题怎么追"。OAuth 把身份、权限、数据范围、审计拆成四件事，各自可验证。

**Q：为什么 MCP Server 是资源服务器，而不是自己做授权服务器？**
A：MCP Server 的职责是执行工具和管数据，签发 token 需要账号体系、登录页、同意页、密钥轮换，这些交给 Keycloak 更稳。自研 AS 在 8 周项目里风险远大于收益。

**Q：scope 校验为什么放在工具层，而不是 HTTP 层？**
A：HTTP 层只判断"是否已登录"，因为不同工具的权限粒度不同；`whoami` 任何登录用户都能调，`archive_document` 需要 `kb.admin`。放在工具层离业务最近，也更容易写测试。

**Q：越权为什么返回 404 而不是 403？**
A：403 会告诉攻击者"这个文档存在但你没权限"，等于泄露资源存在性。404 让存在与不存在不可区分。

**Q：token 泄露了怎么办？**
A：三层——短 TTL（5–15 分钟）+ refresh token；Keycloak 侧可撤销会话；审计能定位泄露后的调用。无状态服务端不保存 token，所以撤销要靠 AS。

**Q：限流为什么放进程内？**
A：这是明确的取舍：单机演示够用，实现简单、无额外依赖。多副本时每个副本各有一套预算，严格全局配额要换 Redis。README 的"已知限制"里写了这一点。

**Q：怎么防止 token passthrough？**
A：服务端不把客户端 token 转发给任何上游。需要访问上游时应该用独立凭证或 token exchange。测试里断言 JWKS 请求不带 `Authorization` 头。

**Q：怎么验证 token 的签名？**
A：按 `kid` 从配置的 JWKS URI 取公钥，只允许 RS256；忽略 token 里的 `jku`（否则攻击者能指定自己的密钥服务器）；JWKS 拉取失败返回 503，验签失败返回 401。

**Q：无状态协议对安全有什么影响？**
A：每个请求独立验签，不存在"连接建立后就默认是该用户"的隐式状态；审计按请求聚合更完整；负向测试可以直接对 HTTP 层做，不需要维护会话。

**Q：31 项安全测试是怎么设计的？**
A：先按 STRIDE 列出 10 类威胁，每类至少一条用例；再分成两层——20 条单元测试用 RSA 密钥对和 JWKS 桩验证验签逻辑，11 条打真实 HTTP 端点验证中间件、错误码与审计。后者能抓到单测抓不到的中间件顺序问题。

**Q：如果要做多租户 / 多副本，怎么扩展？**
A：多租户在 `sub` 之外增加 `tenant_id` claim，所有查询与审计按租户过滤；多副本要求服务端保持无状态（已经满足），限流换 Redis，JWKS 缓存可以共享或各自缓存。

**Q：为什么不用 FastMCP？**
A：FastMCP 把 OAuth 封装得比较深，适合快速出 Demo；这个项目的价值恰恰是讲清楚授权链路，用官方 SDK 只多写一百多行，但每一步都能解释。

**Q：这个项目有什么没做完的？**
A：公网域名部署没有做（本地 Caddy HTTPS 已验证），限流是单机实现，CIMD 仍是实验特性所以用预注册 client，演示账号密码仅用于本地。这些都在 README 里写明了。
